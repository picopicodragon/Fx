## プロジェクト概要

本プロジェクトは、経済・金融政策などのマクロ情報をAIが解釈し、独立した反証審査と厳格なリスク管理を経てFX取引を判断する、自動売買システムの開発を目的とします。

主な技術構成は次のとおりです。

- **Python**：経済データ取得、AI分析の制御、リスク管理、監視、取引記録
- **SQLite**：仕様に基づく分析・注文・リスク・障害・API費用の記録（将来的なPostgreSQLへの移行を想定）
- **AI API**：マクロ経済の因果分析、売買仮説の構築、独立した反証審査
- **ChatGPT Web版**：初期開発での調査、仕様設計、テスト事例の作成、人間による分析レビュー
- **MQL4 / MT4 EA**：楽天MT4の利用を想定した注文処理、損切り管理、注文・口座状態の照合
- **Git / GitHub / Codex**：仕様、実装、テスト、変更・承認履歴の一元管理

**注意：** 現在は仕様策定とリポジトリの初期構成を進めている段階です。本番の取引プログラム、楽天MT4との接続、全体の結合試験は**未実装・未完了**です。実口座での取引は許可されていません。

## 基本方針

1. マクロ経済や金融政策、経済指標、市場予想との差、価格への織り込み、反証を踏まえて売買仮説を構築する。固定のニュース点数だけで売買しない。
2. 売買仮説は**別呼び出しによる独立したAI反証審査**を必須とし、十分な根拠や検証がなければ新規売買を保留する。
3. **資金管理・安全停止の制約はAIの判断より優先**し、AIやCodexが独断で緩和・回避できない構成にする。
4. 開発は**共通データ形式・安全基盤 → 経済データ → AI投資判断 → MT4 EA統合 → ペーパートレード → 承認後の本番移行**の順に進める。
5. 仕様ごとにIDを付け、**仕様 → 開発タスク → 実装コード → 受入テスト → 承認記録**の対応関係を追跡できるようにする。
6. ローカルGitとGitHubを併用する。**個人開発**のため、作業ブランチとPull Requestは本人による変更履歴・差分・自動テスト確認のために利用し、第三者レビュアーを要求しない。
7. 通常の実装・テスト・作業ブランチへのコミット・Pull Request作成はCodexに許可する。ただし、**安全仕様の変更、`main`への統合、本番取引の有効化は開発者本人の明示的な判断・承認を必須**とする。

1. **ローカル模擬**：Pythonで価格変動、損益、注文拒否、通信障害、安全停止などを検証する。
2. **MT4デモ接続**：デモ環境が利用可能な場合に、EAによる注文処理、SL設定、口座照合を検証する。
3. **統合ペーパートレード**：経済データ、AI仮説、反証、リスク管理、EAを連携させ、継続運用を評価する。
4. **本番移行審査**：未解決の重大問題がなく、すべての必要条件を満たしたことを確認し、人間が明示承認した場合に限り実口座での運用を許可する。

## GitHub・Codex運用ルール

- 開発は原則として専用ブランチで行い、**自分自身にレビューを依頼する必要はない**。Pull Requestはセルフチェックと変更履歴の記録に使用する。
- Pull Requestには関連仕様ID、変更内容、テスト結果、影響範囲、**本人確認欄**を記録する。GitHub Actionsの自動検証に失敗した場合は統合しない。
- 個人開発では、GitHubの「必須レビュー承認人数」を1人以上に設定すると、PR作成者本人は自身のPRを承認できず統合が止まる場合があるため、**第三者レビューを必須にはしない**。代わりに本人が差分・テスト結果を確認し、手動で `main` にマージする。
- **安全仕様の変更・リスク制限・損切り・停止・復旧・本番モデル採用**は、通常のコード修正と区別し、本人による明示承認と決定記録を要する。
- 自動マージは使わない。安全設定と本番取引の有効化を、PRのマージだけで許可したとみなさない。
- 初期のCIは文書整合性・コード構文等の基礎検査のみで、FX取引安全性を保証しない。実装が増えるごとに仕様IDに紐づく安全テストを追加する。
- GitHubブランチ保護（必須ステータスチェックなど）はリポジトリ設定・プランを確認して適用する。現時点で未設定なら、運用ルールだけで強制できないことに注意する。
- リスク制限、サーバー側損切り、安全停止・再開、本番AIモデルの承認、実口座注文の有効化はCodexが独断で変更しない。
- **第109問**：リスク制限・SL・発注・停止・復旧・AI注文許可は重要機能とし、実装コードと仕様ID・対応テストを `specs/traceability.json` に紐付ける。登録したコードに対応テストがなければCIで失敗する。通常機能への適用は段階的に拡張する。
- **第115問**：原議との照合は安全重要仕様を優先する。損失制限→SL・注文→停止・復旧→イベント・AI注文許可→本番承認の順に原議を抽出・登録し、残る通常機能へ段階的に拡張する。優先順位台帳の検査が通っても、原議の取得や本人承認が完了したことにはならない。
- **第114問**：原議をWindowsローカルへ個別保存する方式と、必要に応じたChatGPTエクスポートを併用。Pythonで明示的な仕様IDのあるユーザー決定候補を抽出し、本人が原文・文脈・機密情報を確認してからGitHubへ限定登録。抽出結果は未承認の候補として扱う。
- **第113問**：設計対話の原議全文はGit管理外のローカルWindows PCに保管し、機密審査・原文照合を終えた必要な決定抜粋だけをGitHubに登録する。仕様ID・原議参照位置を追跡し、原議不明なら未確認として保持する。
- **第112問**：AIが原議と仕様の相違・欠落・未確定事項を洗い出し、原議未入手の項目を未確認扱いとする。安全重要仕様は本人による原議照合と明示承認まで実装用確定仕様としない。専用の照合登録台帳とCIで、根拠不足の承認状態を検出する。
- **第111問**：第1〜110問の決定索引を整備し、安全重要仕様を先に詳細化して原議照合を実施する。確認済みの範囲からPHASE 1を実装し、未確定項目をCodexに推測させない。
- **第110問**：開発完了を「タスク完了」「モジュール検証完了」「フェーズ受入完了」の三段階で管理。安全重要モジュールと全フェーズの最終受入れには本人の明示承認を必須とし、台帳とCIで状態の整合性を確認する。
- CI等の自動テストには疑似データを用い、実口座の認証情報や発注機能を使用しない。**現在の検査は追跡登録・基礎テストであり、取引安全性そのものの検証は未完了。**
- GitHubリポジトリは非公開（Private）だが、**非公開であることは機密保護の十分条件ではない**。
