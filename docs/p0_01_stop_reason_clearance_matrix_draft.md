# P0-01：停止理由別・監視レベル別の解除条件マトリクス（設計ドラフト）

> **実装用の正式な状態遷移表ではない。** この資料はすでに採用されたQ9/10/12/21～24/43～45/80/104/120～122/123～147/168～171/195～199の方針を、同時発生時に誤って解除しないよう整理した**仕様検討と検査用の入力**である。新しい重要安全条件、注文権限、人間承認を付与しない。

関連する機械可読の一覧と合成シナリオ：`specs/p0_01_stop_reason_clearance_matrix_draft.json`。前段の`specs/p0_01_safety_consistency_crosswalk.json`（CW-04/05/06）を継承。

## 1. 混同してはならない三系統

| 系統 | 状態の例 | 復帰の意味 |
|---|---|---|
| **DD監視** | DD2%警告、DD3%重点再評価 | 条件が成立すれば**監視段階のみ**解除候補。DD4/5停止やほかの停止理由は不変 |
| **戦略・成績悪化** | PERFORMANCE LEVEL 1/2/3 | LEVEL 1は原因解消、LEVEL 2はAI再評価＋安全確認後に通常監視へ。LEVEL 3は安全確認＋本人明示承認が必要 |
| **通信障害** | NETWORK L1/L2/L3、隔離失敗 | 再接続・再起動そのものは復旧証明にならない。重大停止・隔離失敗は別々に維持 |

**DD4%・DD5%は監視解除ではなく新規注文停止のラッチ**。数値の一時的回復は解除条件にならない。DD5%時はQ11/Q12の全決済試行・原因分析と本人再開承認を維持する。DD2/3の解除候補は**それぞれDD1.5%未満/2.5%未満が有効なデータで30分間連続**し、Q126～147の時刻・安全検証を満たす必要がある。

## 2. 個別に評価する停止理由と解除ゲート

| 停止理由・監視状態 | 解除に必要な条件 | 自動解除 |
|---|---|---|
| DD2/3監視 | それぞれの厳密な解除閾値・30分間・有効データ・安全検証 | 監視レベルだけ**条件付き可** |
| DD4%新規停止 | 原因別安全確認＋本人明示承認 | **不可** |
| DD5%重大停止 | 原因分析・全決済試行の状態把握＋安全確認＋本人明示承認 | **不可** |
| 成績悪化LEVEL 1 | 原因解消 | 通常監視への条件付き復帰 |
| 成績悪化LEVEL 2 | AI再評価＋安全確認 | 通常監視への条件付き復帰 |
| 成績悪化LEVEL 3 | 安全確認＋本人明示承認 | **不可**。DD一時改善では解除しない |
| 日次損失1.5%停止 | 次のNY17:00取引日＋口座・注文・SL・稼働等の安全検査 | **その理由のみ**条件付き可 |
| 通信L1 | 原因解消・通信/認証/EA/Python/口座等の安全検査 | その理由のみ条件付き可 |
| 通信L2 | 強い原因解消・安全確認は必須。**承認方法の詳細は別途原議照合** | 詳細未確定、無条件復帰不可 |
| 通信L3 | 原因解消・安全確認＋本人承認 | **不可** |
| 通信資源隔離失敗（Q171） | 旧処理完全終了・隔離・時計/通信/リスク等全検証＋本人承認 | **不可**。自動再起動成功だけでは復帰不可 |
| 外部注文結果不明 | ブローカーの注文・約定・残建玉・SLの独立照合。重複・反対売買リスク不明は新規/再送禁止 | **状態不明のまま再送不可** |
| 停止状態・計算情報不明 | 永続停止理由・リスク値・注文状態の完全性復旧と安全検証 | **不明のまま解除不可** |
| 重要イベントによるペア停止 | 発表から15分経過後以降、該当ペアの市場・データ安全確認 | そのペアの停止理由だけ条件付き可 |

この表は**運用上の必要条件**の整理であり、解除を実行するソフトウェア仕様・承認手順は未確定。**誰がいつどの単位で何を承認するか**、権限確認、取消し、期限切れ、競合、SQLite永続化と再起動復元は人間の最終安全仕様承認待ち。

## 3. 複数停止と本番稼働ゲート

停止理由はQ121に従い**別々に保存・解除**する。例えば日次停止が翌取引日に安全確認を通過しても、DD4%停止と本人承認待ちは残る。成績悪化LEVEL 2のAI再評価に合格しても、DD5%停止は残る。通信が復帰しても隔離失敗ラッチが未確認なら維持する。

実装時に必要な最上位の判定は、（A）すべての必要な個別停止解除条件、（B）別のリスク・データ品質・イベント・AI検証・発注前審査、（C）独立したPHASEと実売買有効化の本人承認、を**同時に満たすか**というゲートである。現段階では**（C）は常に不成立**。停止理由が空であっても実売買は無効。

## 4. 合成シナリオを10件用意

機械可読JSONの`synthetic_cases`で検査するべき例を整理した。内容は以下のような**望ましい拒否・停止保持の結果**であり、実装済みコードの実行結果を意味しない。

- 日次停止のみ条件付き解除してもDD4%停止は残る
- DD4/5%はDD改善だけでは残る。決済結果不明時の再送禁止も残る
- 戦略LEVEL 3は安全確認だけでなく本人承認が必要
- 監視LEVEL 2の解除はDD5%停止を変えない
- 通信再接続のみでは通信障害も隔離失敗も解除しない
- 再起動時の停止状態が不明なら新規停止理由を追加して安全側へ
- UUIDの新規発行だけで結果不明な決済を再送しない
- DD2%の監視解除が成立してもDD4%停止を解かない
- 停止理由が0件でもPHASE-1 BLOCKED中は実売買できない

## 5. 重要な未決項目

- **停止理由ID・監視状態の正規形**、口座/通貨ペア/戦略の停止範囲と複数状態の並存方法
- **原子的な記録更新と再起動復元**、複数イベント競合・履歴欠損・DB破損時の処置
- **本人承認の真正性**（操作経路、認証、操作対象、記録、期限、有効性、取り消し）
- **通信L2の再開条件の厳密な出典照合**、通信L3との境界
- **Q120とQ199の整合**。結果不明は盲目的に再送せず、状態照合完了後に初めて再試行適格性を検討する

**安全状態：** `forward_trading_enabled=false`、`implementation_approved=false`、`human_safety_approval=false`、`owner_approved_for_safety=false`、PHASE-1 BLOCKED。`Q109`により実注文・安全重要コードへ進むには、具体的仕様、対応テスト、証拠と本人承認が別途必要。
