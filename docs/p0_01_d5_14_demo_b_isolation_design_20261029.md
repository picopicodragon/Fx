# P0-01 D5-14：独立デモB隔離設計・デモA非干渉計画

作成日：2026-10-29。関連：D5-2一次資料監査、D5-12（G1〜G9）、D5-13（S0/S1・G2）。

**判定：DESIGN_ONLY / NO_GO / PHASE-1 BLOCKED。D5-14は構成設計だけであり、口座作成・MT4実行・設定変更・接続・データ取得・発注を許可しない。**

## 1. 保護対象と脅威モデル

- **デモA（既存）**：既存の楽天MT4デモ環境。MACD Sampleが配置されており、保有ポジションまたは予約注文が存在することを本人目視で報告済み。EAの実行状態、実際の接続状態、注文内容の個別確認は未承認。**デモAへの読み書き・ログイン・EA変更・注文変更を行わない**。
- **デモB（将来構築を検討する別環境）**：口座の新規作成・併存可否も未確認。存在することを前提にしない。必要な独立性が確認できなければ作成しない。
- **本番口座**：本工程に無関係であり、ログイン・パスワード発行・設定変更を一切しない。
- **典型的な干渉経路**：口座の再作成による既存口座への影響、同時ログイン制限、既存端末の上書き、別ショートカットによる同一端末起動、MQL4ファイル/プロファイル/テンプレート共有、Global Variables/Common Files、レジストリ/OSユーザー共有、EAやWindows自動起動、認証情報共有、デモと本番のサーバー選択間違い、注文/建玉対象の取り違え。

「別のインストールディレクトリ」は必要な技術対策の一部であり、**口座・取引状態・MQL4資源・OS側設定の完全な隔離の証明ではない**。

## 3. 隔離アーキテクチャ案（構築禁止の設計段階）

| 層 | デモAの保護 | デモBの将来構成要件 | 証拠・判断 |
|---|---|---|---|
| 口座 | 既存AのID・建玉・注文を変更しない | Aと異なる独立した楽天MT4デモ口座が公式に許容・無干渉と確認できる場合のみ検討 | E1/E2/E3が未解決ならSTOP |
| OS実行 | Aのプロセスや自動起動を変更しない | 可能なら独立Windows仮想マシン/専用OSユーザーを優先。ディレクトリ分離だけの方式は残存リスクを個別審査 | 実行方式の選定を本人レビュー |
| インストール先 | Aの既存インストール先を一切変更しない | B専用の新規パスを事前に計画、Aや本番と重複・上書きしない | 事前の設計台帳で相互排他 |
| MT4データ | Aのprofiles/templates/MQL4/ログ等へアクセスしない | B専用のデータフォルダを別設計。起動後に実在パスを確認する行為は別途承認が必要 | E5は設計のみ |
| EA/EX4 | MACD Sampleの配置・設定・稼働状態を変更しない | B側のEA/EX4/スクリプトも当面配置・起動しない。自動売買ボタンの状態を勝手に変えない | 手順の段階別承認 |
| IPC/共有資源 | Aの共有ファイル・OSレジストリ・通知経路を変更しない | Common Files、Global Variables、共有フォルダ、Task Scheduler、自動起動、共有ソケット・設定参照を使わない設計 | 共用箇所の監査は将来の別承認 |
| 認証/サーバー | Aの再ログインやパスワード再発行をしない | Bの認証情報はA・本番と分離。接続先のRakutenSecurities-Demo識別を事前条件にする | 実際のログインは禁止 |
| 操作対象識別 | Aの口座番号をGitHubやログに露出しない | B用の非機密ラベルで対象環境を識別。口座の同一性は将来の承認後に検証 | 「デモ表示」だけでは識別不十分 |
| 発注 | Aの建玉/予約注文を一切触らない | Bでも注文経路を物理的・論理的に無効化した設計から開始 | 本PRの時点では取引操作禁止 |

**推奨：**可能ならBを専用VM/専用Windowsユーザーに分離する構成を第一候補とする。ただしVM・別ユーザーもブローカーの同時口座制約、共通ネットワーク・共有ディスクを自動的には解決しない。構成候補の比較は設計上で行い、構築は承認までしない。

## 4. ゲートS0/S1と進行条件

- **S0（文書安全境界）**：禁止操作とAの保護対象をレビューしたこと、変更権限が与えられていないことを確認する。これは実環境の非干渉を技術的に実証したという意味ではない。
- **S1-E1**：楽天のMT4デモを対象とする公式回答・公式資料に「異なるデモ口座の同時保持が可能か」を明記。文書URLまたは正式サポートの回答を台帳に記録。一般の楽天FXデモの回答で代用しない。
- **S1-E2**：Bの新規作成・認証・運用が、Aの既存口座・ポジション・予約注文に影響しないという条件と例外を楽天側の証拠で確認する。
- **S1-E3**：同時ログインと端末切替の制約、口座の無効化条件・パスワード再発行の影響を楽天MT4デモの文脈で確認する。
- **S1-TECH**：OS、MT4プログラム、データディレクトリ、認証、MQL4、EA、共有資源を区別した設計図と、誤起動・誤接続の中止基準を本人が目視確認。
- **S1-APPROVAL**：S1が技術・制度面で満たされた場合でも、B作成・インストール・ログイン・読取り・EA実行・注文それぞれについて**別個の具体的な本人承認**を要する。

未回答、曖昧、製品区分が異なる、口座Aの保護を保証できない場合は **S1=NO_GO**。確認のために実際にBを作ることは禁止。公開資料で解消できない場合は楽天の正式窓口への**照会文案を作る**だけに留める（送信も別途本人指示）。

## 5. Stop/Abort 条件

- B作成がAを置き換える可能性、両口座の同時保持制限、再発行でログアウトする可能性が否定できない。
- AとBのインストールパス、データパス、認証参照、共有リソースが識別不能または重複する。
- 接続先がLiveの可能性、口座ラベルの不一致、EAが自動起動する可能性がある。
- エラー・通信障害・スリッページ・注文状態不一致など、本工程外の実行状態を扱う必要が生じる。
- 外部証拠の失効、情報の欠落、第三者が想定外の手順を要求する。

これらは**以後の試験計画を停止する条件**であって、Aの既存EA・注文に対して自動停止/決済を送る指令ではない。既存Aに変更を加えず、人間の独立した判断へエスカレーションする。
