## 1. 注文状態の証拠階層を分離する

**Q199の既決定を守る。** 応答が`RESPONSE_ACCEPTED`でも、約定・建玉・サーバーSLが存在する証明ではない。`RESPONSE_REJECTED`も、実際の注文不存在や取消確定の根拠と断定しない。タイムアウト・通信切断・不正レスポンス・分類不能は`OUTCOME_UNKNOWN`であり、新規注文と無確認の自動再送を停止する。

| 証拠種別 | 想定する情報 | 証明しないこと |
| --- | --- | --- |
| 送信前SQLite状態：`PREPARED` | Q197に従う意図とIDの事前確定保存 | 送信実行・受付・約定・建玉 |
| 送信前SQLite状態：`DISPATCHING` | Q198に従う事前の遷移コミット確認 | 送信実行・受付・約定・建玉 |
| 送信後応答3分類 | `RESPONSE_ACCEPTED`/`RESPONSE_REJECTED`/`OUTCOME_UNKNOWN` | 取引の確定結果、二重発注がないこと |
| ブローカー注文一覧・履歴 | 模擬注文の注文ID・状態・履歴時点 | 全履歴の完全性や注文が存在しないこと |
| 約定履歴 | 全件/部分約定、累積数量、受付時刻の模擬観測 | 保有建玉/SLの最終一致 |
| 建玉一覧・SL状態 | 保有数量・通貨ペア・方向・サーバー側損切りの模擬観測 | 履歴から漏れた注文の不存在や障害からの復旧許可 |

実際のMT4 APIで注文・約定・建玉・履歴がどこまで独立に確認できるか、照会の保証範囲・遅延・重複・識別子の取り方、履歴に限界がある場合の扱いは**未検証・未確定**。オンライン実装はその調査後に、本人の安全仕様承認と対象限定の実装承認を必要とする。

## 2. 境界の概念的な処理順序（仕様で決まっている範囲）

1. 独立反証済みの仮説・Python安全検証・独立停止理由の全条件が成立したと**別途本人承認済み実装で検査可能な場合のみ**発注対象となり得る。今回のPRではそれらを実装しない。
2. Q195–197：1論理操作IDと試行ごとのID、実行意図をSQLiteトランザクションで事前確定しコミット成功確認。曖昧なコミットは新規禁止。
3. Q198：送信直前の独立リスク検査・停止検査後、`PREPARED→DISPATCHING`をトランザクション確定保存し、その成功確認後だけ送信を許可する。**DISPATCHINGだけで送信したとは判定しない**。
4. Q199：発行した操作に紐付く応答は三分岐で**暫定記録**し、注文/約定/建玉の独立したブローカー照合を通さない限り最終状態と同一視しない。
5. 送信前後のどこかでクラッシュ/ネット断/応答欠損があれば、送信済みとも未送信とも決め打ちせず、SQLite・注文履歴・約定・建玉を突合する。照合に必要な範囲が未取得または相反するときは安全性未確認のまま、新規発注と根拠のない再送を停止する。
6. Q171の隔離失敗ラッチやDD4/5・他の本人承認待ち停止理由は、Broker API復旧・`RESPONSE_ACCEPTED`・チェックポイント成功・再起動によって**解除できない**。

これは机上の**設計境界の確認**であり、ブローカーに何を送るか、どの状態へ自動遷移するかの完成実装仕様・承認ではない。追加の正式状態（送信済み・約定・取消など）、冪等性キー、残注文・部分約定管理、照合完了条件・再開権限は未決。

## 3. プロバイダーに依存しない模擬契約

`schemas/offline/mock_broker_evidence.schema.json`は、外部ブローカーAPIレスポンスのコピーではなく、**合成試験データ用**の草稿である。

- `mock_only=true` 固定で実ブローカーから得た証拠を装わない。
- `logical_operation_id`と`attempt_id`を別々に保持し、Q195–196の二層識別に対応する。ID形式の草稿はUUIDv4の発行・一意性保証を実装したという意味ではない。
- `evidence_source`は模擬応答・注文照会・約定履歴・建玉照会を区別する。
- `response_classification`はQ199の三値に限り、別の`order_observation`/`fill_observation`/`position_observation`と**独立に**記録する。
- `evidence_status`は未検証／不完全／矛盾／模擬観測整合に分類する。`MOCK_CONSISTENT`も実ブローカー検証や新規発注許可を意味しない。
- 実運用で必要な署名・元証拠・時刻の信頼性・注文/建玉数量・履歴鮮度・API情報の参照・整合性計算・ファイル保護・保存先等は未設計のため、スキーマ適合のみで正当性確認済みと扱わない。
