# RISK-3P-103〜108：架空損切り額と架空ポートフォリオの1対1引継ぎ照合

作成日：2026-11-06 JST。PR #191のmainマージ確認後、新ブランチで着手。

## 発見した境界

独立Fraction検算により、損切り計算とポートフォリオ計算の数値式が一致することを確認した。しかし、`phase1_three_pair_synthetic_risk.py`の`max_loss_jpy`は呼出側が任意に主張する架空数値であり、同じチケットの`phase1_three_pair_synthetic_stop_conversion.py`による計算損失を**小さく書き換えても、ポートフォリオ側の算術処理が完了してしまう**。元の算術APIがこの引継ぎを検査する仕様でなかったため、テストだけでなく、専用の合成検証関数が必要である。

## 工程

| 工程 | 変更 |
|---|---|
| RISK-3P-103 | `review_synthetic_loss_handoff`を既存の非運用ポートフォリオ計算モジュールに追加。引継ぎの`SyntheticHandoffReview`は成功時も`NO_GO`／`BLOCKED`／停止ラッチtrue・注文禁止 |
| RISK-3P-104 | 1対1の架空チケット→ポートフォリオ取引を、ID・順番・通貨ペア・方向・状態・数量で照合 |
| RISK-3P-105 | 損切り額と申告損失額の**正確な有理数一致**、候補損失・総損失・0.5/1.0%上限超過フラグ一致を検査。元の入力から両方の計算結果も再計算し、過去の結果の流用や書換えを拒否 |
| RISK-3P-106 | 3ペアの架空クォートについて、BID/ASK・観測時刻・スナップショットIDの同一性を要求。別の架空時点を混入させた引継ぎを拒否 |
| RISK-3P-107 | 売買許可・停止解除・再試行などの安全フラグが偽装されていないことを検査。未照合の建玉・未約定・送信中注文、欠損・過大件数・不正な型に対してFail Closed |
| RISK-3P-108 | 29件の合成テスト、Q109の既存2ソースへのテスト追跡追加、RISK-3P-02の旧移行検査対応、CI・PR |

## 使用するデータと制約

全て**架空の3ペアUSD/JPY、EUR/JPY、EUR/USD**、架空契約情報、架空BID/ASK、架空チケット、架空建玉・未約定注文である。関数が同一の架空入力から2つの演算結果を再現しても、実口座の建玉・未約定注文や注文ステータスの独立検証、ブローカー出典の認証はしていない。呼出側が用意する`positions_reconciled=True`等も本番の照合実施記録ではない。

新しい成功値`mock_binding_consistent=True`は**架空データの内部整合性だけ**を意味し、ブローカーの実損失保証、独立データソース、P05／G1審査合格、売買許可ではない。正しい人間承認や認証済みブローカー契約情報の代わりにもならない。

入力金額と元の損切り見積もりは上限40文字、最大128件、96桁演算の既存ルールを継承する。損失額がこの範囲を超える場合は強引に切り捨てず、**照合不可で拒否**する。

## 既存安全条件

**P05 0/8 BLOCKED、G1実0/15、FX-SAF原議0/15、FORM承認0/43、PHASE-1 BLOCKED、runtime NO_GO、safety_hold_latched=true、verified_values=null**を維持する。

1取引最大損失0.5%、同時保有合計1.0%、日次1.5%、DD4%新規停止／5%全決済＋人間承認、NY17:00、通信断・時計異常の停止条件を変更しない。楽天MT4、EA、実口座、建玉、未約定注文、Windowsの私有ログ・認証情報にはアクセスせず、注文・停止解除も行わない。
