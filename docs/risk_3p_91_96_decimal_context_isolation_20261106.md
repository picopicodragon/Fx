# RISK-3P-91〜96：合成リスク計算のDecimal環境分離と整合性回帰

作成日：2026-11-06 JST。PR #189がmainへマージ済みであることを確認して、新ブランチで実装。

## 発見と改善の理由

前工程までに、3ペア合成リスク計算器2本でDecimal演算の精度を96桁へ強化した。ただし `with localcontext() as context: context.prec=96` は**呼出元のDecimalコンテキストを継承する**。精度だけを変更しても、親側の指数上限`Emax`、指数下限`Emin`、丸め方向、`Inexact`／`Rounded`／`Overflow`等の例外設定が残る。例えば架空の大きな通貨脚を計算すると、`Emax=9`の親設定から本来不要なOverflow例外を受ける余地がある。コードの安全性検証が呼出元の設定に依存するべきではない。

そこで `scripts/phase1_three_pair_synthetic_risk.py` と `scripts/phase1_three_pair_synthetic_stop_conversion.py` を `with localcontext(Context(prec=96))` へ変更した。**新規の独立したDecimalコンテキスト**で計算し、元のコンテキストは維持する。小数演算の許可精度、0.5%／1.0%の上限比較自体は変えない。

## 計算の独立性に関する限界

ここでいう「独立コンテキスト」は**Python Decimalの演算設定についてのみ**の話であり、第三者によるブローカーデータの独立証明ではない。2本の計算器が同じ架空金額を返しても、架空の`max_loss_jpy`入力、実効ストップ、約定、手数料、ギャップ、スリッページの真偽は証明されない。

今回のID制約は合成データが改行・制御文字を持ち込むことを拒否する狭い防御であり、汎用の秘密値検出や個人情報検査ではない。

合成G1確認用ペアはUSD/JPY、EUR/JPY、EUR/USD。過去に正式指定した4取引ペアの運用要件を変更するものではない。既存の架空ポートフォリオ検証が本番注文を可能にすることもない。
