# 原議照合・差分管理ルール（Q112）

> **状態：レビュー工程の設計・記録開始。原議との全面照合・安全重要仕様の本人承認は未完了。**
>
> 本文の「原議」とは、ユーザーが各設計設問（Q1〜Q112）に対して実際に採用を表明した会話記録を指します。AIによる要約、過去のメモ、README、マスター索引だけを原議として扱わないでください。

## 正式に採用した方式

1. **AIによる事前照合**：原議のユーザー発言と `MASTER_SPEC.md`・機能別仕様の記述を突合し、一致・矛盾・省略・未確定点を抽出する。
2. **根拠の区別**：原議を直接閲覧できた場合は `ORIGINAL`、要約のみなら `SUMMARY_ONLY`、参照不可なら `UNAVAILABLE` と記録する。AIが原議を確認したと偽らない。
3. **判定の区別**：`MATCH`（一致確認）、`DISCREPANCY`（相違）、`OMISSION`（欠落）、`NEEDS_CLARIFICATION`（意味・数値・運用が未確定）、`SOURCE_UNAVAILABLE`（原議未確認）を別々に記録する。
4. **優先度**：資金管理、DD/日次損失、発注、SL、停止・復旧、AI注文許可、実口座稼働制限は `SAFETY_CRITICAL`。これらは**本人が実際の原議と草稿・解釈を確認し、明示承認するまで「実装用確定仕様」としない**。
5. **変更時の保存**：修正案、関連仕様ID、引用根拠または原議の所在、判断理由、未解決事項、承認証拠をGitHubで追跡する。
6. **安全上のブロック**：相違・欠落・原議不明・承認未了の安全重要仕様に関わる本番注文ロジックは着手を保留。安全基盤の**純粋なシミュレーション・データ構造や未接続のテストハーネス**等は、未確定条件を仮定しない範囲で段階開発できる。
7. **承認の本人性**：AIやCodexは承認を代理入力してはいけない。承認記録があることの機械検査と、本人が実際に意思表示したことの確認は別。GitHub PRを自分でマージしたことだけでは安全仕様の内容や本番稼働を承認したとみなさない。

## ステータスの意味

| 項目 | 意味 |
|---|---|
| 原議 `ORIGINAL` | 決定を示す当時のユーザー発言を直接確認した |
| 原議 `SUMMARY_ONLY` | 記憶・後日要約を参照したが原議には未アクセス |
| 原議 `UNAVAILABLE` | 原議の取得ができず、確認待ち |
| 照合 `NOT_REVIEWED` | AI比較未着手 |
| 照合 `MATCH` | 原議と当該草稿の一致を根拠付きで確認 |
| 照合 `DISCREPANCY` | 草稿と原議が異なる |
| 照合 `OMISSION` | 原議にある重要な条件が草稿から欠落 |
| 照合 `NEEDS_CLARIFICATION` | 原議の決定だけでは実装条件が一意に定まらない |
| 照合 `SOURCE_UNAVAILABLE` | 比較元を入手できず確認保留 |

**注意**：`MATCH` はAIによる照合結果であり、安全重要仕様の本人承認（`owner_approval`）とは別です。`MATCH` の有無にかかわらず重大な食い違いや新たな技術上の疑問が見つかれば受入れを停止します。

## 安全重要仕様の承認条件

`specs/reconciliation_registry.json` の `safety_critical=true` の項目を `implementation_approved=true` にする条件：

- `source_kind=ORIGINAL`
- `comparison_status=MATCH` または原議の確認に基づいた `RESOLVED`（差分解決済み）である
- `source_reference` と `spec_reference` に根拠の所在が明記されている
- `owner_approval` に `approved_by`・`approved_at`・`decision_reference` が記録されている
- 関連する未決の安全パラメータが解消済みである

**CIは記録形式と相互関係しか検査できず、捏造された承認の真正性までは検証できません**。承認操作を実際に人間の意思表示に紐付ける運用を別に必要とします。

## 実行手順

1. 原議の対話内容（必要箇所を抽出・保存したファイルでも可）を、機密を除いて確認可能にする。
2. モデルは原議から厳密な数値・例外・停止条件・承認要件を抽出する。
3. GitHubの草稿との差分表を作り、どの資料にも裏付けのない値を**作り足さない**。
4. 通常の記述誤りは訂正案をPRに記録。安全重要仕様は本人へ判断を求める。
5. 承認後、`MASTER_SPEC.md` と機能別仕様・トレーサビリティ台帳を同期して、確認済みの安全範囲からのみPHASE 1の実装チケットを準備する。
