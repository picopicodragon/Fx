# 開発受入れ・完了判定ルール（Q110）

状態：**運用ルールの初期版**。実装モジュールは未完了であり、`main`への統合や本番取引を承認した記録ではありません。

## 完了の三段階

| 階層 | 完了の意味 | 最低限の証拠 | 承認者 |
|---|---|---|---|
| LEVEL 1 / TASK | 指定仕様に沿った実装と単体テストが完了 | 仕様ID、ソース変更、テストID、テスト結果、CI結果 | 通常はCodexが記録可能。ただし安全機能は上位審査が残る |
| LEVEL 2 / MODULE | 関連タスクの完了、機能結合・障害系・互換性の検証が完了 | 統合試験記録、エラー処理・リスク評価、対象タスクの証拠 | 安全重要機能は**開発者本人の明示承認が必須** |
| LEVEL 3 / PHASE | フェーズの要求を満たし、未解決問題を評価し、受入れが完了 | モジュールの結果、フェーズ受入れ項目、本人の承認記録 | **すべてのフェーズで開発者本人の明示承認が必須** |

**注意：** LEVEL 1が完了していてもLEVEL 2・3の完了を意味しません。フェーズが受入れ済みであっても**本番売買の開始承認とは別**です。

## 記録状態

- `NOT_STARTED`：作業未開始
- `IN_PROGRESS`：実装や試験を実施中
- `TESTED`：必要なテスト結果が揃い、受入れ確認待ち
- `ACCEPTED`：当該LEVELの完了条件を満たす
- `BLOCKED`：不具合、データ欠落、仕様未決、未承認などで進行不能

安全重要機能・フェーズは、テストが成功しただけで `ACCEPTED` に変えてはいけません。**本人承認の証拠（承認日・承認した対象・記録先）が必要**です。

## 検証可能な証拠

記録には、関連仕様ID、開発タスクID、変更コミット/PR、テストID、実行日時・成功/失敗の結果、未解決の問題、承認者（必要時）を添付します。PRだけで承認を代用しません。

## 継承ルール

1. MODULEは関連TASKがすべて `ACCEPTED` であり、モジュール結合・異常系テストが成功した後でなければ `ACCEPTED` にできません。
2. PHASEは関連MODULEがすべて `ACCEPTED` であり、フェーズ受入れ結果と本人による明示承認が記録された後でなければ `ACCEPTED` にできません。
3. MODULEが安全重要機能に属する場合、本人による明示承認なしでは `ACCEPTED` にできません。
4. 不明・欠落・異常がある場合は `BLOCKED` か検証中の状態に戻し、完了を宣言しません。
5. 問題修正や仕様変更で前段階の根拠が無効になったときは影響するLEVELの受入れを取り消し、再検証します。
6. GitHub Actionsが管理ファイルの形式と整合性を検証しても、テスト結果の妥当性や本人の本当の意思を自動的に証明することはできません。

## 初期管理ファイル

`specs/acceptance_registry.json` は、タスク・モジュール・フェーズをそれぞれ別に記録する初期台帳です。現在のフェーズはすべて `NOT_STARTED` として登録し、完了と誤解しないようにします。

`scripts/check_acceptance.py` は台帳の一部の形式と依存関係を自動検査します。**取引機能の安全性や承認権限の本人性を技術的に保証するものではありません。**
