# 第115問：安全重要仕様の原議照合・登録順序

> **決定：C（安全重要仕様優先）**  
> **状態：着手順序の確定。原議の実際のローカル保存・逐語照合・安全重要仕様の本人承認は未完了。**

## 基本原則

過去の設計対話を仕様ID別に抽出するときは、**損失制限、サーバー側SL、注文、停止、復旧**に関する原議を優先する。次にAI判断・経済情報・通常機能へ広げる。転記だけでは原議照合や実装承認にならない。

原議全文はWindows PC上のGit管理外に保管し、GitHubには本人が確認し機密審査を終えた必要最小限の**ユーザー発言**だけを置く。現在利用可能な原議が要約のみの場合は「原議確認済み」にしない。

作業順は `specs/source_review_priority.json` で管理する。これは**原議を集める順序**であり、Codexによる取引コード作成の許可順ではない。

## 各仕様IDの原議照合手順

1. `docs/local_archive_guide.md` を参照してWindowsのローカル原本を保存し、ファイルが取得できた事実を確認する。**現時点では全原本未取得**。
2. Pythonツールで対象会話だけから決定候補を抽出する。「CでOK」のような短い返答は前後の質問を人間が確認し、AIの推測で原議を捏造しない。
3. 原本、原文抜粋、`MASTER_SPEC.md`、`specs/safety_foundation.md`を比較し、内容の一致・相違・欠落・未決事項を記録する。
4. 照合が済んだ部分を、機密確認を経て `specs/source_excerpts/Qxxx.md` に登録する。要約と原文は同じファイルでも明確に区別する。
5. `specs/source_evidence.json` に原議参照・照合根拠を追跡可能な形で記録し、`specs/reconciliation_registry.json` の未解決課題を更新する。
6. 安全重要仕様は、**原議の確認＋仕様差異の解消＋必要テストの定義＋本人の明示承認**を別途要求する。これらを経ていないときは実装用の確定仕様としない。
7. 各バッチが確認済みになった後、AI判断・経済データ・通常機能の原議へ段階的に対象を拡張する。**自動的に本番取引を開始しない。**

## ステータス

| 値 | 意味 |
|---|---|
| `PENDING_ORIGINAL` | 原議が未取得、または原本の文脈・完全性が未確認 |
| `EXCERPT_VERIFIED` | 対象の原議抜粋を原本と照合した状態。**実装用承認ではない** |
| `NOT_REVIEWED` | 仕様文書との比較が未実施 |
| `DIFFERENCE_FOUND` | 相違または欠落があり、未解決 |
| `COMPARISON_MATCHED` | 原議と当該仕様の一致を根拠付きで確認 |
| `OWNER_APPROVED` | 別管理の安全仕様承認条件まで満たした場合のみ付与 |

機械検査は形式や参照整合性の確認であり、原文の真正性・AIの解釈・本人の意思表示を自動証明できません。
